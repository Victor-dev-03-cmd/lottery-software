C-1. Outstanding Balance Destroys Itself After Every Payment
-------------------------------------------------------------
File   : src/services/database.ts — syncInvoiceLiveBalance (~line 1005)
Symptom: After the SECOND payment on any invoice, the outstanding balance shown
         on the Ledger, Dashboard, Reports, Alerts, and PrintExport pages is
         understated. After several payments the balance may read Rs. 0.00 even
         though the agent still owes money.

What is broken:
  syncInvoiceLiveBalance reads the current outstanding_balance column, subtracts
  all payments, then WRITES the result back into the same column. The next time
  it runs, it starts from the already-reduced value and subtracts all payments
  again — doubling the deduction.

  Example:
    Invoice outstanding_balance = Rs. 10,000
    Payment 1 of Rs. 3,000 saved → column becomes Rs. 7,000  (correct so far)
    Payment 2 of Rs. 2,000 saved → live = 7,000 − 5,000 = Rs. 2,000  (WRONG)
    Correct answer: Rs. 10,000 − Rs. 3,000 − Rs. 2,000 = Rs. 5,000

Fix:
  The outstanding_balance column must be treated as an IMMUTABLE SNAPSHOT set at
  invoice creation and NEVER overwritten. Remove the
    "UPDATE invoices SET outstanding_balance=? WHERE id=?"
  write inside syncInvoiceLiveBalance. All live-balance queries already recompute
  the correct value on the fly from invoice_total — simply stop writing back.

C-2. Deleting a Payment Does Not Restore the Balance
-----------------------------------------------------
File   : src/services/database.ts — deletePayment (~line 1063)
Symptom: After a payment is deleted, the agent's outstanding balance remains
         permanently lower than it should be. In multi-payment scenarios the
         balance can be driven to zero by deleting a single payment entry.

What is broken:
  This is a direct consequence of C-1. C-1 has already overwritten the
  outstanding_balance column with a reduced figure. When deletePayment then
  calls syncInvoiceLiveBalance it finds the already-reduced column and subtracts
  zero (no payment rows left), so the balance stays at the wrong lower value.

  Example:
    Invoice Rs. 10,000, Payment Rs. 3,000 saved → column becomes Rs. 7,000
    Payment deleted → syncInvoiceLiveBalance runs → 7,000 − 0 = Rs. 7,000
    Balance stays Rs. 7,000 forever. Correct answer: Rs. 10,000.

Fix:
  This is automatically resolved when C-1 is fixed. Once the column is never
  overwritten, deletePayment can call syncInvoiceLiveBalance safely — it will
  find the original invoice_total and subtract only the remaining payments.

C-3. Confirming a Large Invoice Only Decrements One Stock Batch
----------------------------------------------------------------
File   : src/services/database.ts — confirmInvoice (~line 2412)
Symptom: Inventory counts are inflated after every large invoice confirmation.
         Physical stock audits will never reconcile with system counts.

What is broken:
  When an invoice is confirmed, the FIFO logic issues a single SQL UPDATE with
  LIMIT 1, targeting only the oldest batch. If the invoice quantity exceeds
  what remains in that one batch, the overflow is silently dropped — no error,
  no warning, no partial decrement on the next batch.

  Example:
    Invoice qty = 250 for "Mega Power"
    Batch A has 100 remaining, Batch B has 200 remaining.
    After confirm: Batch A distributed_qty += 100 (capped by MIN)
    Batch B: untouched. 150 tickets were never deducted.
    Inventory now shows 150 more tickets available than actually exist.

Fix:
  Replace the single UPDATE with a loop. For each invoice line item, query all
  batches for that game ordered oldest-first, then consume the required quantity
  greedily across batches until qty reaches zero, updating each batch
  individually. Raise an error (and block confirmation) if available stock
  across all batches is less than the invoice quantity.

C-4. Cancelling an Invoice Restores Stock to the Wrong Batch
------------------------------------------------------------
File   : src/services/database.ts — cancelInvoice (~lines 2456, 2459)
Symptom: Cancelled invoices do not release stock correctly. Available inventory
         for a game stays lower than it should be, potentially blocking new
         invoices unnecessarily.

What is broken:
  cancelInvoice unconditionally picks the oldest batch ("ORDER BY batch_date
  ASC LIMIT 1" with no condition on remaining space). But confirmInvoice picks
  the oldest batch that STILL HAS STOCK ("AND (total_qty - distributed_qty) >
  0"). After Batch A is fully used up, new confirmations go to Batch B. When
  those invoices are later cancelled, the system tries to restore to Batch A
  (which was never touched by those invoices). Because Batch A's distributed
  count may already be at its minimum, the MAX(0,...) guard silently absorbs
  the subtraction and Batch B's inflated count is never corrected.

Fix:
  Track which batch(es) were decremented at confirm time — either by storing
  batch IDs on the invoice record at confirmation, or by mirroring the greedy
  FIFO loop in reverse during cancel (going from newest batch back to oldest
  and restoring the same amounts that were taken).

C-6. PIN Lockout Can Be Bypassed Indefinitely
---------------------------------------------
File   : src/components/PinModal.tsx (lines 88-90)
Symptom: The advertised 5-attempt / 59-second lockout provides zero protection
         against anyone physically at the device.

What is broken:
  The attempt counter and lockout timer are stored as local React state inside
  the PinModal component. Every time the user closes the modal (Cancel button
  or clicking outside), React destroys the component and the counters reset to
  zero. An attacker can:
    - Try 4 wrong PINs
    - Close the modal
    - Reopen the modal (counters reset to 0)
    - Try 4 more wrong PINs
    - Repeat indefinitely

  With 10,000 possible 4-digit combinations, all can be cycled through in
  approximately 10-15 minutes with no lockout ever firing.

Fix:
  Move the attempt counter and lockout expiry OUTSIDE the modal component.
  Options (in order of security):
  1. Module-level variable in usePinGuard.ts (survives unmount/remount)
  2. sessionStorage (survives modal close, clears on window close)
  3. Rust backend begin_admin_session command with OS-level rate limiting
     (most secure — cannot be reset by any frontend action)

C-7. Commission Counted Twice When Default and Agent-Specific Schemes Both Active
----------------------------------------------------------------------------------
File   : src/services/database.ts — getProfitSummary (lines 1947-1962)
Symptom: Profit Analytics shows total commission and net profit that are wrong
         by the full commission amount for every invoice belonging to any agent
         who has both a specific scheme and a default scheme active.

What is broken:
  The commission calculation joins invoices to commission schemes using:
    (cs.agent_id = i.agent_id OR cs.agent_id IS NULL) AND cs.is_active = 1
  When both a per-agent scheme AND a default (NULL) scheme are active, every
  invoice for that agent matches BOTH rows. The SUM therefore adds both
  commission amounts — doubling the total. Net profit is understated by the
  full duplicate commission amount.

Fix:
  Replace the OR join with a correlated subquery that picks the most specific
  matching scheme first (agent-specific before NULL default). Example:
    COALESCE(
      (SELECT rate FROM commission_schemes
       WHERE agent_id = i.agent_id AND is_active = 1 LIMIT 1),
      (SELECT rate FROM commission_schemes
       WHERE agent_id IS NULL AND is_active = 1 LIMIT 1)
    )

H-14. Admin PIN Crackable in Under 1 Second from a Database Backup
------------------------------------------------------------------
File : src/hooks/usePinGuard.ts (lines 5-11)
Issue: PINs are hashed as SHA-256(pin + "_nimalsiri_2026"). SHA-256 is extremely
       fast. The salt is a fixed, publicly known string in the source code. Only
       10,000 four-digit combinations are possible — a complete lookup table can
       be computed in under one second. Anyone with access to the SQLite database
       (device theft, cloud backup, insider) can recover the admin PIN immediately.
Fix  : Move PIN verification to Rust and use bcrypt or Argon2 with a randomly
       generated per-record salt. The begin_admin_session command already receives
       the hash — hash on the Rust side using a KDF instead.
